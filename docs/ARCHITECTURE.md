# Architecture｜架构说明

DealScope 采用本地双工作台架构，把“广泛发现”与“深入核验”分开。两个界面共享文件缓存、证据约束和来源元数据，但承担不同决策阶段。

## 组件责任

| 组件 | 责任 | 不负责 |
|---|---|---|
| `app/radar_app.py` | 七日雷达 UI、刷新状态、公众号文章库 API | 不直接把搜索摘要当事实 |
| `weekly_radar.py` | 来源编排、七日窗口、事件门禁、失败降级 | 不做完整尽调或收益预测 |
| `wechat_discovery.py` | 生成发现查询、调用可插拔搜索后端、保留查询与渠道来源 | 不将发现次数解释为独立确认 |
| `wechat_source_pool.py` | SQLite 去重、预览导入、凭据过滤、事务写入 | 不登录微信、不执行网络抓取 |
| `wechat_article_fetcher.py` | 获取允许的公众号原文并输出结构化结果 | 不保存登录凭据 |
| `app/app.py` | 深度评估 UI、后台管线状态、人工 URL 输入 | 不在请求线程内同步跑完整管线 |
| `collectors/url_capture.py` | URL 安全检查、最终地址复核、原文与截图保存 | 不信任重定向目标或搜索摘要 |
| `llm_extract.py` | 可选结构化抽取、引文回指 | 失败时不制造“看起来合理”的证据 |
| `score_engine.py` | 证据归一化、门禁、维度诊断和结构化排序 | 不输出投资收益预测 |

## 两条主流程

### A. 周度发现

1. 公开搜索后端返回标题、摘要和 URL，仅标记为 `discovery_only`。
2. URL 规范化去重，同时保留 `provider` 和 `discovery_query` 作为发现来源。
3. 原文读取成功后，真实发布日期、正文缓存和最终 URL 写入本地文章库。
4. 只有正文与真实日期都可用的记录才进入七日窗口。
5. 事件规则、主体识别和投资主题匹配生成最多 5 个候选；不足时保留空位。
6. 所有来源失败时保留上次成功报告，并单独记录本次尝试。

### B. 深度评估

1. 用户从周度雷达带入公司，也可手工填写研究主题和原始 URL。
2. 浏览器采集层逐次校验初始 URL、DNS 与重定向目标，保存正文和来源元数据。
3. 抽取层生成结构化事实；引文必须能在保存正文中逐字找到。
4. 证据层检查主体、日期、来源等级、独立确认和负面信号。
5. 评分层根据证据支持度输出结构化初筛、风险缺口和下一步核实项。
6. 若本轮没有形成可用证据，不覆盖上一份成功报告。

## 本地状态

```text
data/input/                 用户主动提供的 URL
data/raw/                   原文快照与采集元数据
data/wechat_pool/           SQLite 文章库与正文缓存
data/output/weekly_radar.json
data/output/latest_report.json
data/output/latest_attempt.json
```

公开仓库不应包含这些运行时目录中的真实内容。`scripts/load_demo.py` 只会生成带有 `synthetic: true` 的演示缓存。

## 可靠性策略

- 长任务由进程内互斥锁保护，重复点击返回 busy，而不是并发覆盖文件。
- JSON 报告使用同目录临时文件、`fsync` 和原子替换。
- SQLite 写入使用事务；导入流程先 preview，再按文件指纹确认。
- 成功报告与最近一次刷新尝试分开保存，失败状态不会伪装成成功。
- UI 根据 `window_end` 与 `generated_at` 计算缓存龄期。

## 扩展点

- 新搜索后端实现 `SearchBackend` 协议，而无需改变证据门禁。
- 新来源类型先输出统一的原文记录，再进入抽取和评分层。
- 新评分维度应同时定义证据需求、客观门禁和反例测试。
- 若演进为多人服务，需要新增鉴权、任务队列、租户隔离、数据库迁移和审计日志；当前架构只承诺本地单用户使用。
